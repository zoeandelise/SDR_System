# 4 系统实现

## 4.1 系统功能实现

### 4.1.1 用户注册

注册页面为新用户提供账号创建入口，页面设有用户名、昵称、密码和确认密码等表单字段。用户填写完信息后点击注册按钮，系统校验用户名是否已被占用以及两次密码输入是否一致，校验通过后将用户信息写入数据库。注册成功后自动跳转至登录页面。

注册功能主要实现代码如下：

```java
@PostMapping("/register")
public AjaxResult register(@RequestBody RegisterBody registerBody) {
    String username = registerBody.getUsername();
    String password = registerBody.getPassword();
    SysUser sysUser = new SysUser();
    sysUser.setUserName(username);
    if (userService.selectUserByUserName(username) != null) {
        return AjaxResult.error("注册用户'" + username + "'已存在");
    }
    sysUser.setNickName(registerBody.getNickName());
    sysUser.setPassword(SecurityUtils.encryptPassword(password));
    return toAjax(userService.insertUser(sysUser));
}
```

### 4.1.2 用户登录

用户在登录页面输入用户名和密码后提交，后端接收请求后查询数据库验证账号信息。验证通过后系统生成JWT令牌返回给前端，前端将令牌存储在本地，后续请求均携带该令牌用于身份验证。若账号或密码错误则返回提示信息。

登录功能主要实现代码如下：

```java
@PostMapping("/login")
public AjaxResult login(@RequestBody LoginBody loginBody) {
    String token = loginService.login(
        loginBody.getUsername(),
        loginBody.getPassword(),
        loginBody.getCode(),
        loginBody.getUuid()
    );
    AjaxResult ajax = AjaxResult.success();
    ajax.put(Constants.TOKEN, token);
    return ajax;
}
```

### 4.1.7 智能推荐功能

智能推荐是本系统较为重要的一个功能模块。用户点击获取推荐按钮后，后端按照一定的流程进行筛选。首先加载用户的健康档案，根据其中的疾病标签和过敏源信息对食物库进行过滤，将不适合该用户食用的食物排除在候选范围之外。例如对于标记有高血压的用户，系统会过滤掉含有红烧、腌制、麻辣等关键字的高钠类菜品；对于标记有海鲜过敏的用户，系统会将虾、蟹、鱼等相关食物一并排除。完成安全过滤后，系统判断用户的历史记录数量，如果历史数据较少则采用基于热量匹配的基础推荐，否则通过协同过滤的方式从偏好相近的用户食谱中提取候选项。最终结果经去重处理后返回给前端展示。

主要实现代码如下：

```java
@GetMapping("/recommend")
public AjaxResult getRecommendation() {
    Long userId = SecurityUtils.getUserId();
    SysUserHealth health = userHealthService.selectByUserId(userId);
    List<DietFoodInfo> safeFoods = filterByHealthRules(health);
    List<DietRecord> records = dietRecordService
        .selectRecordsByUserId(userId);
    List<DietFoodInfo> result;
    if (records.size() < COLD_START_THRESHOLD) {
        result = fallbackRecommend(safeFoods, health);
    } else {
        result = collaborativeFilterRecommend(
            safeFoods, userId, records);
    }
    result = applyRepetitionPenalty(result, records);
    return AjaxResult.success(result);
}
```

### 4.1.8 推荐模型管理

推荐模型管理页面为管理员提供了一个对推荐算法进行管理和调试的入口。页面分为模型管理、推荐分析和模拟推荐体验三个功能区。模型管理区以卡片形式展示协同过滤模型和内容推荐模型的加载状态，管理员可以选择模型类型和训练数据范围后启动异步训练，训练过程中页面会实时轮询并展示每个模型的进度百分比和当前步骤。推荐分析区通过ECharts绘制算法采纳率饼图和各引擎转化率柱状图，为管理员提供一些基本的效果参考。模拟推荐体验区允许管理员输入用户ID、餐次类型、过敏源、疾病标签和食量等参数后发起推荐测试，系统返回推荐食物列表及对应的营养参数，同时在下方通过ECharts力导向图展示协同过滤的用户相似度关系网络，以较为直观的方式呈现推荐的来源逻辑。

模型训练的主要实现代码如下：

```java
@PostMapping({"/model/train", "/training/start"})
public AjaxResult startTraining(
        @RequestBody Map<String, Object> params) {
    List<String> modelTypes = params.containsKey("modelTypes")
        ? (List<String>) params.get("modelTypes")
        : Arrays.asList("collaborative_filtering",
            "content_based");
    Integer trainingDays = params.containsKey("trainingDays")
        ? Integer.valueOf(
            params.get("trainingDays").toString())
        : 180;
    mlRecommendationService.trainModelsAsync(
        modelTypes, trainingDays);
    Map<String, Object> result = new HashMap<>();
    result.put("modelTypes", modelTypes);
    result.put("trainingDays", trainingDays);
    result.put("message",
        "训练已启动，共" + modelTypes.size() + "个模型");
    return AjaxResult.success("训练已启动", result);
}
```

## 4.2 核心推荐算法设计

本系统标题中明确提出了“基于协同过滤算法”，但在实际健康饮食领域中，单纯的推荐算法极易造成安全隐患。例如，系统可能会将高糖食物推荐给口味相近的糖尿病患者。为了尝试解决这一问题，本系统在核心算法层面设计了“安全过滤 + 偏好推荐”的双层串联机制。

### 4.2.1 安全过滤机制原理

安全过滤作为推荐流程的前置卡点，其核心思想是“一票否决”。当接收到用户请求时，系统首先提取用户的健康档案属性，查询其是否带有特定的疾病标签或过敏源。随后，系统加载待推荐食物库库，将食物所含的常量营养素（如含糖量、嘌呤量、脂肪）与系统预设的疾病警戒阈值进行对照。

这一规则引擎的代码实现主要通过逻辑分支与数值比对完成。若某种食物（如海鲜）匹配到了用户的过敏源标签，或者其升糖指数（GI）超过了高血糖设定的安全上限，该食物将被从候选集中剔除。经过安全筛查后的食物子集，才能获准进入下一阶段的偏好推荐计算，这种机制在一定程度上降低了饮食推荐的安全风险。

### 4.2.2 基于用户的协同过滤推荐机制

在确保了候选食物列表的基础安全性后，系统采用基于用户（User-Based）的协同过滤算法来进行个性化的评分测算与推荐排序。为了兼顾学术严谨性与系统实际业务场景，本系统将抽象的协同过滤理论与“饮食打卡”等具体业务结合，其算法落地流程分为以下三个步骤：

**1. 基于隐式行为的用户-食物评分矩阵构建**

在经典的推荐算法体系中，首先需要构建一个反映用户偏好的矩阵。传统做法是要求用户显式打分（如1-5星），但这种要求在实际应用中会极大增加用户的操作负担。因此，本系统通过挖掘用户客观的“饮食打卡”记录，提取隐式评分。
理论上，对于“某位用户”和“某样食物”，其隐式评分可以通过该用户在一定周期内摄入该食物的打卡频次来量化。打卡频次越高，代表偏好度越高。通过系统后台对所有用户打卡记录的自动统计，可以构建出一个规模为“系统总用户数 × 数据库总食物数”的稀疏评分矩阵，这就形成了一张无需用户额外操作的全员偏好数据表。

**2. 用户相似度计算与近邻群体发现**

有了偏好矩阵后，系统需要寻找与“目标用户”口味最相似的其他用户群体。在数学理论上，本系统底层采用余弦相似性（Cosine Similarity）来进行计算。

（注：系统实际计算时，通过对比两个用户共同打卡过的食物频次乘积，除以各自打卡频次的平方根之积来求得余弦值）

在通俗的业务场景中，可以将两个用户的饮食偏好得分想象为空间里的两条线，余弦公式就是为了计算这两条线夹角的大小。例如，“目标用户”和“对比用户”在打卡中都经常记录“全麦面包”和“黑咖啡”（产生过丰富的共同交集），那么他们的夹角就会很小，算出的“相似度得分”就会无限接近于 1。系统会按分数从高到低排序，把具有最高相似度得分的前列用户保留下来，划分为目标用户的“同味近邻群体”。

**3. 结合安全过滤的推荐评分预测**

当需要给目标用户生成推荐列表时，系统会从其“近邻群体”喜欢的食物中进行挑选。此时，前置的“安全过滤机制”依然有效，会把“近邻群体”喜欢但目标用户存在疾病冲突的危险食物剔除掉。对于剩下既安全又受近邻偏好的食物，系统通过加权平均的逻辑去预测目标用户可能给出的评分。

加权推算的核心逻辑是：近邻用户与目标用户的“相似度得分”越高，其对该食物的打卡偏好对最终预测结果的影响权重就越大。
简单地说就是：如果这群口味极其相似的“饭搭子”都很频繁地打卡吃“西兰花牛肉”，而目标用户从来没吃过，系统就会预测出该目标用户去吃“西兰花牛肉”时也能获得很高的满意度。最终，系统按推算的预测评分由高到低倒序排列，截取前置食物推送到用户的推荐体验页面中，从而实现安全与个性化并重的推荐闭环。

## 4.3 本章小结

本章对系统各功能模块及核心算法的设计与实现过程进行了说明。从用户端和管理员端来看，系统基本涵盖了注册登录、健康档案、打卡记录、目标追踪以及运营管理等全套功能。在本章中，不仅通过示例展示了前台页面的布局形态及部分后端接口逻辑，更在算法层面详细拆解了“安全优先，协同偏好”的双层推荐机制设计思路——如何利用规则过滤规避疾病隐患，并采用基于用户的协同过滤模型来测算个性化食物评分。各功能模块与算法核心之间通过统一的数据总线协作贯通，较为完整地支撑了饮食推荐系统方案的落地。
