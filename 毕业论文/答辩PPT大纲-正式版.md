## 第3页 · 研究背景与意义

**背景（论文1.1.1节）：**
- 慢性代谢性疾病发病率攀升，中国人群超重和肥胖率较40年前上升约3倍
- 现有饮食管理应用三大不足：功能冗余问题突出、推荐安全性不足（无法根据疾病史做成分级过滤）、数据孤岛
- 国家"健康中国2030"规划纲要鼓励信息技术应用于健康管理

**意义（论文1.1.2节）：**
- 应用价值：降低用户获取个性化膳食指导的门槛，数百毫秒内完成安全校验和推荐计算
- 学术实践：覆盖软件工程完整生命周期，锻炼协同过滤与规则过滤融合的工程能力

## 第4页 · 国内外研究现状

**国外（论文1.2.1节）：**
- 产品成熟（MyFitnessPal等），数据百万级，支持条形码录入和图像识别
- 算法前沿：深度学习建模饮食序列、隐语义因子分解
- 局限：训练成本高、冷启动差、中西饮食差异大

**国内（论文1.2.2节）：**
- 建立了含中式烹饪方式的食物数据库
- 走规则引擎+轻量协同过滤的务实路线，可理解性高、落地成本低
- 不足：疾病过滤粗糙，如糖尿病模式粗暴屏蔽整个甜品分类，未精细到升糖指数逐一比对

**本课题定位（论文1.2.3节）：**
- 【重点高亮】在单机可运行的协同过滤基础上，研究**疾病敏感成分过滤与协同过滤推荐相结合**的个性化推荐框架

## 第6页 · 系统架构设计

**B/S架构 + 前后端分离（论文3.1节）：**
- 四层结构：表现层 → 业务层 → 数据访问层 → 数据库层
- 前端：Vue + Element UI + ECharts + Axios异步请求
- 后端：RuoYi框架（Spring Boot + MyBatis + Shiro）
- 数据库：MySQL（InnoDB引擎，支持事务和行级锁）
- 权限：JWT令牌鉴权 + Shiro权限框架 + RBAC角色模型
- 开发环境：IntelliJ IDEA，Java语言

**技术选型理由：**
- RuoYi内置权限控制、代码生成、日志记录，节省开发时间
- 协同过滤用Java Stream API和Collection API实现，无需GPU资源

## 第8页 · 核心推荐算法设计（重点页）

**双层串联架构（论文4.2节）：安全过滤 + 偏好推荐**

**第一层：安全过滤（论文4.2.1节）**
- "一票否决"机制：过敏源标签命中即移除、疾病标签触发营养素阈值比对
- 糖尿病→升糖指数过滤、高血压→高钠食物/烹饪方式过滤、痛风→嘌呤含量过滤、高血脂→胆固醇过滤
- 过滤后生成安全候选食物集

**第二层：协同过滤推荐（论文4.2.2节）**
- 步骤1：基于隐式行为构建用户-食物评分矩阵（挖掘饮食打卡频次，无需用户显式打分）
- 步骤2：余弦相似度计算用户相似度，发现"同味近邻群体"
- 步骤3：加权平均预测目标用户对候选食物的评分，按分排序推荐

**【重点高亮】安全网机制（论文3.3.4节）：**
- 推荐结果返回前端前，执行后置安全网过滤，再次逐条核查过敏源和疾病禁忌

## 第9页 · 智能推荐完整流程

展示论文图3.5智能推荐获取流程图

四阶段流程（论文3.3.4节）：
1. **用户画像加载**：读取健康档案 + 统计近期饮食偏好
2. **安全过滤**：过敏源一票否决 + 疾病标签营养素阈值过滤 + 高血压烹饪方式过滤
3. **推荐算法调度**：优先协同过滤 → 历史数据不足时降级为热量匹配基础推荐
4. **后置安全网校验**：最终结果再次逐条过滤确保安全

## 第12页 · 总结与展望

**研究成果（论文第6章）：**
- 实现了管理员+用户双角色完整业务流程
- 实现了疾病规则硬过滤与用户协同过滤相混合的分层推荐策略
- 前端Vue+ECharts实现数据可视化，后端RuoYi实现快速开发

**不足与改进方向（论文第6章，如实列出）：**
- 协同过滤在用户量和食物种类多时性能有所下降，可考虑矩阵分解等降维方法
- 食物营养数据库条目相对较少，可后续接入权威营养数据开放接口
- 推荐反馈信息粗略（仅记录采纳与否），可加入评分、评价等多元反馈
